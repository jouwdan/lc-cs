# Test the website

Check the site from a user’s point of view.

1. Restore the original records and run the server. Complete this short test table:

| Action | Expected result |
|---|---|
| Empty search | 4 books |
| `river` or `RIVER` | 2 River titles |
| `volcano` | Clear no-match message |
| `Stars &` | Stars & Stories; Available |
| Tab to input, type, then Enter | Search works without a pointer |

2. Zoom the browser to 200%. Narrow the window. Check that the label, button, status, and long titles remain readable and that focus has a visible outline.
3. Keep the page open but stop the server. Submit a search. Expect a message saying the books could not be loaded and asking you to check the local server. Restart and retry.
4. Ask a partner to find one available book. Record whether they succeed and one point of confusion. Make one small improvement and repeat the same task.
5. Write four sentences: user need; your change; evidence from a test; one limit. The server uses fictional, read-only, in-memory data. It is not a persistent school library system.

**Optional server-boundary test:** the page limits input to 100 characters, but callers can bypass it. Use the supplied `--check` option on the restored baseline to verify that an oversized direct request gets HTTP 400. Explain why page validation alone is insufficient.

For your ALT evidence, keep the schema, one search trace, a before/after change, and the test table. Be able to explain the path yourself rather than only show a screenshot.
