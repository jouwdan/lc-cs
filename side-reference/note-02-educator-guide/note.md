# Teacher guide

Plan lessons and give useful feedback.

This page is teacher guidance. Students can go straight to the <a href="https://tutors.dev/course/lc-cs">course route</a> or <a href="https://tutors.dev/lab/lc-cs/side-reference/book-01-study-journal">study journal</a>.

## A repeatable lesson

For a 60-minute lesson, try: retrieve an earlier idea (5 minutes), explain (12), predict a worked example (8), practise (25), quiz (5), reflect (5). Adjust to your class. Longer tasks span sessions; the flexible allocation below is a flexible outline, not a requirement to finish every optional activity.

Model one decision aloud, then let learners predict the next step. Give a short core task with a visible expected result. End with one repair rather than only a score. The six resource labels provide a route: Learn → Practise → Check → Answers → Exam practice → Recap.

## Prerequisites and practical contexts

Teach representation alongside Python, functions before recursion, and tracing before efficiency. Lists/files support analytics; validation/testing support a database application. Start embedded work with simulated or recorded inputs, then calibrate real devices where available. Revisit ethics, access and security in each practical.

The four ALTs can share ideas, but retain distinct evidence: database retrieval, a data investigation, a model experiment and embedded input/output. Topic 15 begins with one existing artefact, so learners are not asked to complete four projects in a single workshop. Keep collaborative practice separate from individually assessed coursework.

## Support and challenge

Offer a vocabulary list, first trace row, small dataset or partly completed program. Ask learners to explain the missing step, then remove the support for another attempt. Record support without treating one result as a permanent level decision.

For challenge, change one assumption or ask for a counterexample: empty inputs, duplicates, missing readings, tied modes or a misleading graph. Higher Level work should extend reasoning, not just program length. The official specification's bold clauses determine level distinctions.

## Give useful feedback

Point to the evidence, name the gap and assign a small next task. Example: “Your count is correct, but the final run is missed. Trace a list whose longest run ends at the last item.”

For portfolio practice, use the <a href="https://tutors.dev/note/lc-cs/topic-15-project-portfolio/note-01-learn">same five-area, 20-point classroom rubric in Topic 15</a>: need/requirements, implementation, testing/improvement, communication/contribution, and responsible choices. Score 0–4 in each, with evidence. It is **not an SEC marking scheme**. For other labs, a requirement/result/next-step comment may be more useful than marks.

Check reasoning/design as well as output: a trace, model, pseudocode or interface plan should connect to the user's need. Check normal, boundary and invalid cases. Attractive presentation cannot replace correctness or independent explanation.

## Inclusive access

Core concepts have text routes. Optional media has written alternatives; use captions when available. Offer paper traces, readable text, spoken descriptions of diagrams and shared hardware roles. Do not rely on colour alone. Check web interfaces with a keyboard, visible focus and associated labels. Each learner should interpret results and write or test code.

## Solutions, tools and assessment

Solutions are public for self-study. Prepare separate unseen tasks for graded classroom work. Ask learners to explain a section, predict a change and show their iterations. Where assistance is permitted, record its role and verify the output. Follow the actual assessment rules for help, supervision and authentication.

For historic exam practice, use the matching year/level scheme. The index maps 176 English question groups; multipart questions may span topics. It does not separately translate the Irish versions. Inspect the original PDF for diagrams and exact wording. Schemes can allow alternatives; discuss uncertain judgements instead of treating a model answer as the only wording permitted.

## Optional 180-hour teaching allocation

This is a flexible teaching suggestion, not an official timetable. Adjust it for your class and the actual assessment schedule. Revisit programming and ethical questions throughout.

| Topics | Focus | Suggested hours |
|---|---|---:|
| 01–04 | Study habits, systems, representation and networks | 30 |
| 05–09 | Algorithms, Python, data structures and testing | 50 |
| 10–13 | Data, models, embedded and interactive systems, including ALT practice | 55 |
| 14 | Society, history, accessibility and AI | 10 |
| 15 | Applied tasks, project process and reflection | 20 |
| 16–17 | Revision, practice assessment and past papers | 15 |

One possible sequence introduces Topics 01–09 and a small data/web task in year one, then revisits programming while extending Topics 10–15 in year two. Reserve time for assessed coursework according to the current brief. Short student-session estimates are stopping-point suggestions within this broader plan.
