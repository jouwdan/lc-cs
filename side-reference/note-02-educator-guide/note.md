# Teaching and assessment guide

A practical teaching plan for a mixed class, with explicit success evidence and support routes.

## A lesson you can repeat

Start with five minutes of retrieval from an earlier topic. Demonstrate one worked example while verbalising the decisions. Ask learners to predict the next step before revealing it. Move to a guided lab, then remove one scaffold for an independent task. End with a brief quiz and a correction, not just a score.

For a 60-minute lesson, a suggested split is 5 minutes retrieval, 12 explanation, 8 worked prediction, 25 practice, 5 quiz and 5 reflection. Longer labs span multiple lessons. These timings are teaching suggestions; adjust them to your group and equipment. Use the 180-hour plan in Topic 01 as a flexible course outline.

## Sequence and prerequisites

Teach representation and Python basics alongside each other so a variable has both a value and a representation. Introduce functions before recursion and tracing before efficiency. Teach lists and files before analytics; teach validation and testing before a web/database application. Begin embedded work in a simulator or with recorded data, then calibrate and test real devices. Revisit ethics, accessibility and security inside every practical context.

The ALTs can overlap topics: the data investigation draws on file handling and testing, while a sensor project supplies data for a model. Preserve the distinct learning evidence for each ALT rather than renaming the same task four times. Keep the individual assessed coursework separate from shared practice solutions.

## Support and challenge

For learners needing support, give a vocabulary bank, a completed first trace row, a small concrete dataset and a partially completed program. Ask them to explain the missing step. Next remove the scaffold while keeping the same concept. Avoid assigning a permanent level based on one diagnostic.

For challenge, change a precondition or ask for a counterexample. Use duplicates, empty collections, missing readings, tied modes or a misleadingly plausible graph. Higher Level learners should explain efficiency and limitations in unfamiliar settings, not merely write longer programs.

## Feedback rubric for original practical tasks

This is a classroom rubric, not an SEC marking scheme. Score each dimension 0–3: 0 missing; 1 partial with substantial errors; 2 mostly correct with evidence; 3 correct, justified and independently checked.

| Dimension | Evidence expected |
|---|---|
| Problem definition | Clear inputs, outputs, constraints and success criteria |
| Reasoning/design | A trace, model, pseudocode or interface plan tied to the need |
| Implementation | A working solution with understandable structure |
| Testing | Normal, boundary and invalid cases; expected and actual results |
| Explanation/evaluation | Causal explanations, limitations and a supported improvement |
| Responsible practice | Accessibility, synthetic/minimised data, source acknowledgement and individual contribution |

Give a specific next task for the weakest dimension. Do not confuse attractive presentation with correctness. Test demonstrations should include the awkward cases, not only the happiest path.

## Inclusive access

All essential concepts appear as selectable text; external media has a written alternative. Use captions if viewing, enlarge text as needed, explain diagrams aloud and provide a paper tracing route. Do not rely on colour alone in graphs or gates. Test interfaces using a keyboard, visible focus and associated labels. Plan shared hardware roles so each learner interprets readings and writes or tests code, rather than one learner doing every technical task.

## Responsible use of solutions and AI

This repository publishes solutions for self-study. Use different unseen tasks for graded work. Ask learners to explain a short section, predict a change and show their own iterations. If permitted tools assist learning, record their role and verify their output; an unexplained correct-looking program is not evidence of understanding. Follow the actual assessment's rules on assistance and authentication.
